# 下一阶段：从需求实现到可靠建筑编译

日期：2026-10-04。状态：阶段性实施路线，不代表以下能力全部实现。

第一批已接入[建筑需求契约与构件归属](../BUILDING_REQUIREMENT_CONTRACT.md)：保护可识别的明确要求、保存方案验证结果、分配 component_id 并让楼梯与卫星对齐优先读取 host_id。逐栋作用域、统一已解析模型及最终方块验收仍待实施。

## 结论

优先推进「显式需求契约 + 统一的已解析建筑模型 + 主体/附属关系与空间约束」。随后投入立面与屋顶生成语法。内部只保留基本楼层、楼梯和连通性。

目标不是覆盖所有想象中的建筑，而是让支持范围内的要求可表达、可编译、可核查；不支持或相互冲突的要求明确说明，不能静默改写为另一栋建筑。

## 推荐链路

用户描述 → 建筑需求 → 建筑关系与设计方案 → 已解析建筑模型 → 几何约束校验 → 方块合成 → 需求验收与预览 → 确认放置。

BuildingProfile 提供设计参考；PlanProgram、components、assembly 和 typology 为兼容入口或底层几何工具。已解析模型是这些入口共同遵守的编译契约，不是第五个独立生成器。

### 1. 建筑需求作为不可丢失的输入

记录每项要求的稳定编号、原文片段、类型、值、单位、作用对象、来源、是否明确、是否允许调整。区分：

- 必须满足：明确指定的尺寸、层数、材料、屋顶类型、入口朝向、连接关系、禁用项目。
- 优先满足：宽敞、古朴、轻盈等需解释的偏好，转换为可调整的设计目标。
- 可以推断：未指定的窗距、屋顶坡度、局部材料变化。

优先级为用户明确要求 > 世界及工具硬边界 > 推断与研究建议 > 装饰默认值。若前两者冲突，应解释不可同时满足，而不是悄悄更改用户要求。语义不足但可合理推断时直接生成；只有影响可行性的关键歧义才追问。

示例：「两栋建筑相距8格」必须确认或声明解释为外墙之间净距还是中心距；不能在几何阶段各算一种。「每层高度5格」需要统一楼板标高和可用净高，避免把两者混用。

### 2. 建筑模型以对象关系代替散落坐标

建议对象类型：building、mass、level、facade、roof、opening、connector、circulation、decoration。

每个对象有 id、host_id、local_frame、role、source_requirements。关系示例：屋顶覆盖主体 A；窗户开在 A 的南立面、二层、第三开间；连廊连接 A 二层东端口与 B 二层西端口；楼梯连接本主体的一、二层。

层高、屋顶接触面、窗户位置和桥接标高由主体派生。LLM 负责提出体量、风格和关系；编译器负责确定整数坐标及一致尺寸。不能要求模型分别猜出每个附属构件的世界位置。

保留局部坐标，但用明确 local_frame 指向建筑/主体/立面，坐标只转换一次。现有中心与 min_corner 通过适配器转换；新方向规范采用 Minecraft 方位，旧立面方位必须经过版本化适配，不直接批量替换字符串。

### 3. 编译合成控制覆盖权限

在生成 PlannedBlock 之前保留来源和区域角色：主体壳、楼板、屋顶、开口、通行、装饰。合法操作需要声明对象和范围：

- 门窗可切对应墙面，楼梯可切对应楼板洞口。
- 室内净空不得清除外墙；外梯需显式声明外部关系。
- 装饰不能替换主体壳、必要支撑或占据保留通道。
- 连廊先确定两个连接端口，再派生楼板和开口，禁止只靠坐标接近判断连接。

处理顺序不是万能规则：同位置最后补丁仍可作为合法操作的执行语义，但构件覆盖是否合法需要在此前判定。不是把任何交叠都判为错误；穿插体量、悬挑和建筑连接有明确许可关系。

第一版使用整数几何计算、候选位置枚举和规则校验即可。只有多体量布局约束复杂且现有求解失败率可量化时，评估 CP-SAT 等求解器，不立即增加依赖。

### 4. 外观语法是第二项主工作

优先形成参数化设计规则，而不是继续堆砌零散装饰：

- 体量：矩形、圆塔、L形、U形/院落、双栋及连接；约束主体比例和明确的错层/退台。
- 立面：按楼层与开间划分墙面；确定基座、主墙、窗带、腰线和檐口的关系；主入口独立分配开间。
- 屋顶：完整屋面、屋脊、坡度、出檐、接触面，以及多个体量屋顶的交接；明确禁用时不生成冠部。
- 风格：以体量比例、窗洞节奏、屋顶形态和构件尺度表达，材质只是其中一层。

先完善石砖住宅、木石建筑、圆塔、中式屋顶与现代平顶等可复用外观规则。建筑内部不扩展复杂房间、家具或高级楼梯系统。

## 技术研究与取舍

1. CGA 形状语法适合从体量逐层细化立面与建筑壳，并表达构件之间的上下文关系。建议借鉴其分层生成方法，复用项目已有屋顶、立面和构件库，不直接移植完整语言。[ETH Procedural Modeling of Buildings](https://emeritus.icu.ee.ethz.ch/research/demos/procedural-modeling.html)
2. SceneCraft 先建立场景关系图，再把关系转成数值布局，并使用渲染反馈迭代。推论：FormaCraft 适合借鉴「关系先行、编译后校验、局部修复」，但 Blender 场景效果不能证明 Minecraft 方块建筑满足要求。[SceneCraft 论文](https://arxiv.org/abs/2403.01248)
3. CP-SAT 处理整数约束，并区分可行、不可行和未知状态。适合未来多栋布局、间距和端口候选的组合求解；不应拿超时或 UNKNOWN 当成需求不可行。[Google 官方 CP-SAT 文档](https://developers.google.com/optimization/cp/cp_solver)
4. SIGI 从网格三维建筑样例学习可解释形状语法，论文包含 Minecraft 应用。它适合较后阶段的风格规则和范例库研究，需要先有可靠的语义、构件归属和评价数据。[SIGI 论文](https://arxiv.org/abs/2109.10217)

现阶段不推荐把主要资源用于大模型微调、端到端图像转体素、任意模型生成脚本或大规模多智能体系统。这是基于当前故障与工程成本的判断；并非这些技术无价值。优先把可验证的建筑编译框架建好。

## 分批推进与验收

| 批次 | 交付物 | 必须可核查的结果 |
|---|---|---|
| A：需求与身份 | 版本化需求契约、对象 id/host_id、旧计划适配、兼容性样例 | 显式层数/层高/尺寸/屋顶/材料不被丰富化覆盖；每个派生构件有主体归属；不能解析时给出具体诊断 |
| B：统一解析与边界 | ResolvedBuildingPlan（建议名称）、楼层/立面/端口关系、局部坐标转换和覆盖权限 | 单栋/圆塔/双栋的主体、屋顶、楼板、入口与连接坐标一致；室内净空不切外墙；强制确认不能绕过语义硬约束 |
| C：外观规则 | 开间与立面规则、屋顶接合、少量可靠风格族 | 窗户有连续墙面承载，屋顶覆盖并接触主体；相同设计种子可重放；多样性不改变硬要求 |
| D：验收与局部修复 | 需求逐条报告、失败定位、依赖对象局部重编译 | 能说明哪些要求满足/调整/不支持；改屋顶只影响屋顶及依赖项，不重随机整栋；真实预览和放置结果可追溯 |

评测从当前六次真实响应及常见矩形、圆形、L形、院落、双栋、坡地扩展。建议建立约30类需求样例，每类固定至少3个设计种子；每次记录需求、计划、几何摘要和必要的固定视角图。这是拟定基准，不是已有覆盖率。

硬要求对所有判为可行且返回成功的用例必须通过；不能以「预览成功」或总体测试数替代。结构校验使用实际占用/表面关系，不把整个包围盒误当实体，也不把合法窗洞算缺墙。审美和风格相似度另行人工评审；视觉模型可辅助发现问题，不能覆盖几何硬校验。

## 第一批推荐实施范围

先实现 A 的最小闭环：一栋建筑与两栋建筑；需求只涵盖尺寸、层数、层高、材料、屋顶、入口、禁止装饰、连廊关系。规范化输出对象身份与 host_id，并适配回现有 components 编译入口，保证游戏可运行。暂不重写所有生成器。

将启发式丰富化降为默认建议，最近主体匹配保留为旧格式兜底并记录诊断。为后续统一解析预留接口，同时写清 PlanProgram 是场地组织输入、Component 是几何兼容输入、ResolvedBuildingPlan 是共同的建筑事实模型。现有文档按这三个职责校准，避免继续并列宣称多条路线都是最终架构。
