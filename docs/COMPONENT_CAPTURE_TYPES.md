# 捕获类型与流程审查

## 发现的问题

1. 分类位于第三步，选择之前已经在配置选区和锚点，无法提前提供合适的安装与方向提示。
2. 原分类切换强制清除 manualAttachment，覆盖用户安装方式；GENERIC 又保留上一类的默认值，导致通用构件继承门窗的墙洞和内外要求。屋顶细部也统一推荐墙面，缺少屋面/屋脊等合理建议。
3. 分类、名称和标签没有纳入取消捕获的恢复范围，取消后部分编辑仍残留。
4. 保存请求发送前就 commitCapture，失败时草案已被视为提交完成；应在成功回执后提交，并避免等待期间重复发送和改动提交内容。
5. 原捕获请求使用单包字符串传输，较大的构件 JSON 会超过限制。现复用有界分块上传会话，由服务端验证捕获快照后入库；点击保存即授权此次捕获提交，不再重复弹出文件导入确认。
6. 从库中加载构件后开始捕获，原 useLibrary 状态可能让工具继续放置已加载构件。捕获期间明确进入草案模式，取消时恢复原模式；未选类型或等待保存时禁止世界操作。面板每帧清除未显示控件的命中状态，避免隐藏按钮和输入框继续响应。

## 类型模型

保留 ComponentCategory 作为粗粒度语义基础，新增独立的 type 引用（稳定 key 与显示 label）。预设以数据表管理，不为每个建筑细节新增 enum 或专用生成代码。首批覆盖门、窗、阳台、栏杆、面板、柱、装饰柱、楼梯、斗拱、拱券、装饰、屋顶细部、烟囱、屋脊与通用构件。

自定义类型填写 1–64 字符名称，默认粗类 GENERIC，也可选择行为基础类。自定义 key 由规范化名称计算，不依赖文件名或资产 ID。类型是检索分类，不授予拉伸、镜像、材质替换或开洞权限；风格与套系仍使用各自字段/标签。相同结构和使用规则只改变类型名称时仍可去重，来源记录保留各自分类。

缺少 type 的程序化定义可由 category 取得基础类型；提供 type 时必须验证 key、label 和基础类的一致性。自定义类型可用于库搜索及显式 assetType 查询筛选，不把类型名称自动拼进权限标签。

预设 key 稳定，显示名称允许本地化；自定义名称先进行 Unicode 与空白规范化，拒绝控制字符及不完整代理字符。查询字段为 semantic.assetType，可填写完整类型 key 或规范化后精确匹配的名称。界面搜索同时考虑经验证来源中的 typeAliases；硬标签和变形权限不因此扩展。

## 捕获界面

先显示预设网格和“自定义类型”，用户明确选择类型后展开原有选区、锚点、语义及作者权限步骤。已有选区可保留，不要求重新框选。捕获中允许改类型，位置、连接位、变形规则不随分类变化而重置。

预设提供安装/方向建议，只有尚未手动设置的字段自动更新。通用/自定义的自动建议明确为自由安装、无方向性，避免继承上一类。用户可显式恢复类型建议；该操作不清除选区或作者变形权限。自定义名称与基础类可继续编辑，不需要修改模组代码。

类型、名称、标签与编辑模式进入捕获取消快照；手动安装/方向标志随草案复制、提交和取消恢复。等待保存回执时冻结提交快照，成功提交，失败保留可重试草案，断线解除等待。

## 保存边界

捕获上传使用独立 CAPTURE_START 操作和同一套有界分块会话，服务端重新生成上传者命名空间、CAPTURED 来源与未指定的许可/训练授权，不信任客户端声明。JSON 上限为 200 万字符，上传信封上限 16 MiB，分块上限 20 KiB；缩略图校验 PNG 头和 IHDR，最多 1 MiB、宽高各不超过 1024。复用已有资产时保留原缩略图。确认提交前可取消，提交阶段禁止重复保存和取消；失败释放等待状态并保留草案。

## 自动验证与游戏内验收

隔离构建的构件相关测试共 211 项，失败与错误均为 0。新增类型、捕获状态、检索和持久化测试共 20 项，覆盖类型建议与手动设置、取消恢复、保存快照、分类去重与来源别名、无效类型和图片边界，并以超过旧字符串限制的 600 方块样例验证分块捕获保存。

游戏内仍需检查：不同面板宽度下的类型网格与滚动、中文自定义名称输入和焦点、类型切换后的标记操作、提交进度/断线重试，以及单人和独立服务器的实际保存回包。自动测试没有替代这些交互验收。

本次按开发阶段的新模型实现，不增加旧资产迁移。真实游戏内网格、输入焦点、滚动及服务器往返仍需验收。
