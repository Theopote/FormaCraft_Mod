# 建筑类型与风格体系推进

## 本批结果

现有能力清单见 `CAPABILITY_INVENTORY.md` 与机器可读的 `CAPABILITY_INVENTORY.json`。审计覆盖15项风格配置、10项结构类型、材料目录和文化卡片的标识关联。来源为实际资源目录和解释器注册源码，未把配置存在认定为视觉验收通过。

`proportion_hints.architecture_intent` 记录原始描述、用途、风格、结构、显式材料、否定要求和词法作用域。要求优先级的目标为：用户明确描述、用途规则、风格默认、材料默认。当前版本是意图观察层，不替换既有路由、主体布局和风格生成规则；不能仅凭该字段认定图书馆已具备阅览室。

每条风格观察记录来源短语和位置；左栋、右栋及第N栋按文本分段保存，并不自动绑定组件顺序。部位标记目前识别主体、屋顶、立面、外墙、室内。多种风格保留为多条观察，不猜测混合权重。白墙与玻璃不会自动推导出现代风格，哥特式也不会自动推导出教堂用途。未知流派保留原文，避免被默默改成某个已知流派。

## 类型、风格与规则卡

用途卡应描述功能空间和通行关系；结构卡描述承重与空间骨架；风格卡描述比例、轮廓、构件及可选装饰。地域/时代作为风格变体单独处理，不能用“中式”覆盖所有中国建筑。材料选择可以改变外观，但不能替代风格所需的几何特征。

规则卡的统一字段建议：

- 身份：稳定ID、显示名、中英文别名、版本、来源。
- 适用条件：用途、结构骨架、尺度、层数、场地。
- 形态规则：体量比例、平面组织、屋顶轮廓、入口和门窗节奏。
- 构件规则：必需特征、可选特征、不兼容组合、小尺度简化方案。
- 材料：各部位默认、候选与明确材料覆盖。
- 用户覆盖：哪些是默认建议，哪些属于结构可行性检查。
- 证据：配置完成、路由接入、方块几何回归、游戏视觉验收分别记录。

## 已知需要整理的衔接

文化卡片原有11条目录外引用现已分类：2个历史别名、5个独立变体身份和1个编辑意图，共覆盖11条卡片引用。共享身份目录为 `style_identity_catalog_v1.json`，Python意图观察与配置查询、Java风格配置查询、文化卡片构建校验均读取该目录。历史别名映射到现有配置；变体保留身份，不自动套用另一种风格。

唐代木构、传统中式、乡村小屋和两种体育场变体尚未新增专用风格配置。身份审计通过只表示引用可解释，不表示形态实现或游戏验收完成。`Patch_Edit` 单独归类为编辑意图。中文别名与标识大小写在配置查询时统一，未知名称仍保留原文。

`StyleIntentResolver` 的形态分支使用 GOTHIC/HUI/CHINESE/JAPANESE/INDUSTRIAL/MODERN/DEFAULT 分类，统一风格目录则有15项，二者不是一一对应。下一批需逐项追踪通过材料、StyleGenome、风格规则及专用生成器实际产生的特征，避免“只识别名称”和“有可辨识形态”混为一谈。

## 扩展顺序

1. 建立统一别名与风格变体关系；核对文化卡片和Java/Python路由。
2. 优先完成住宅、公共大厅、商业、工业四类用途卡，明确尺度与空间关系。
3. 在已有生成基础上细化现代国际主义、徽派、中式庭院、哥特式；每项至少有可验证的屋顶/立面/比例特征。
4. 实现建筑级和部位级绑定，支持同一请求左右两栋不同风格，避免全局材料覆盖局部描述。
5. 扩展地域/时代及混合风格；未知风格优先保留用户特征并给出能力说明。

## 验收矩阵

| 组合 | 观察重点 |
|---|---|
| 同一住宅 × 不同风格 | 屋顶、体量比例、门窗节奏有可解释的区别 |
| 同一风格 × 住宅/图书馆/工厂 | 用途和空间组织不同，不仅更换名称或材料 |
| 左栋徽派、右栋现代 | 风格与材料分别绑定，不能互相覆盖 |
| 现代主体、日式屋顶 | 记录混合意图，部位清楚，结构兼容 |
| 指定石砖的现代建筑 | 显式材料优先，几何特征仍表达现代风格 |
| 不要哥特式、不要装饰 | 否定要求保留，不由风格默认重新添加 |
| 小尺度、坡地、水岸 | 关键风格特征简化后仍可辨认，入口和室内可用 |
| 未知流派 | 保留原文，不宣称已有专用生成器 |
